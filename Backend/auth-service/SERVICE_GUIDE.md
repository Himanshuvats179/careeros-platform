# Auth Service - Comprehensive Service Guide

## 1. Executive Summary (What this service does in 5 lines)
1. Manages user registration, BCrypt password hashing, and login credentials verification.
2. Generates HMAC-SHA256 signed JWT access tokens and 7-day refresh tokens.
3. Implements Redis token blacklisting to immediately revoke access tokens on logout.
4. Enforces Role-Based Access Control (RBAC) across CANDIDATE, RECRUITER, and ADMIN roles.
5. Emits `USER_REGISTERED` and `USER_LOGGED_IN` audit events to Apache Kafka.

## 2. Why This Service Exists
The Auth Service acts as the security perimeter for CareerOS. It issues signed JWT claims, manages refresh token rotation, and handles password verification, keeping credentials completely isolated from business services.

## 3. Microservice Dependencies & Interactions
- **API Gateway (`:8080`)**: Validates JWT signatures generated by Auth Service before forwarding requests.
- **Service Registry (`:8761`)**: Eureka dynamic instance registration.
- **Apache Kafka (`:9092`)**: Published topic `careeros.auth.events` consumed by Audit Service.
- **Redis (`:6379`)**: Stores blacklisted access tokens on user logout.
- **PostgreSQL (`:5432`)**: Stores `users`, `user_roles`, and `refresh_tokens`.

## 4. Package & Folder Structure Explanation

### `com.careeros.auth.controller`
- **Why Controller exists**: Exposes REST endpoints (`/api/v1/auth/register`, `/api/v1/auth/login`, `/api/v1/auth/refresh`, `/api/v1/auth/logout`, `/api/v1/auth/me`).

### `com.careeros.auth.security`
- **Why Security exists**: Encapsulates `JwtTokenProvider` (token generation & signature validation) and `CustomUserDetailsService` (Spring Security details loading).

### `com.careeros.auth.service` & `impl`
- **Why Service exists**: Contains registration logic, BCrypt hashing, refresh token rotation, Redis blacklisting, and Kafka event publishing.

### `com.careeros.auth.repository`
- **Why Repository exists**: Provides data access for `User` and `RefreshToken` entities.

### `com.careeros.auth.entity`
- **Why Entity exists**: Maps `User` and `RefreshToken` tables with soft delete (`is_deleted`) and optimistic locking (`@Version`).

## 5. End-to-End Request Flow
1. Client sends `POST /api/v1/auth/login` with email and password.
2. `AuthController` passes payload to `AuthenticationManager`.
3. `DaoAuthenticationProvider` verifies BCrypt password hash.
4. `JwtTokenProvider` generates HMAC-SHA256 access token with claims (`userId`, `email`, `roles`).
5. Refresh token created, saved in PostgreSQL `refresh_tokens` table, and returned to client.
6. `AuthEvent` (`USER_LOGGED_IN`) published to Kafka topic `careeros.auth.events`.

## 6. Senior Interview Questions & Production Patterns
- **Q: How do you handle JWT token revocation in a stateless architecture?**
  - *Answer*: On logout, the token signature is placed into a Redis key `blacklist:<token>` with a TTL matching the token's remaining expiration time. Gateway filters verify Redis before routing requests.
